## 2. Resposta direta à pergunta de escopo

> **A Microsoft publica uma lista autoritativa de colunas do dataset clássico de cost details?**
> **SIM — mas apenas os NOMES e a ORDEM das colunas, por tipo de contrato e versão de dataset.**

O índice oficial de schemas ("Cost Management dataset schema index") lista arquivos de schema por
dataset e por contrato, com a respectiva versão. Para cada combinação existe uma página com uma
tabela numerada de colunas e descrições. Portanto, **os nomes das colunas não são reconstruídos
nem inferidos: são citáveis** e estão em §4.

O que a Microsoft **NÃO** publica para o dataset clássico:

- **tipo de dado por coluna** (não há coluna "DataType" em nenhuma das páginas do dataset clássico; a página equivalente do dataset FOCUS *tem* essa informação);
- **nullability / obrigatoriedade** de cada coluna;
- **unidade** por coluna;
- **formato exato de timestamp** por coluna;
- **enumeração completa de valores permitidos**;
- **schema de "métrica"**: não há uma página separada para *actual* e outra para *amortized*. Existe **um** schema de "Cost and usage details" por contrato, e o portal oferece actual/amortized/escolhas de métrica sobre ele.

Consequência metodológica: **as colunas estão VERIFIED quanto ao nome; todos os demais atributos
estão **não publicados** / `UNVERIFIED`** e o simulador **não deve** inventar tipo, unidade ou formato
para elas. Ver §5.

### 3.1 Convenção de atualização de dados (relevante para fidelidade temporal)

- Runs diárias do dataset de cost and usage produzem **duas execuções por dia nos primeiros cinco dias do mês**: uma com os dados do mês corrente e outra (não visível no run history) com todos os custos do mês anterior. Motivo documentado: "latent usage and charges are included in the invoice up to 72 hours after the calendar month is closed."
- Ajuste de arredondamento (*rounding adjustment*) é emitido **no nível de billing profile (MCA) ou enrollment (EA)** quando a fatura é gerada, com `MeterCategory`, `MeterSubCategory` e `ChargeType` iguais a `RoundingAdjustment`. Campos válidos no registro: `BillingAccountId`, `BillingAccountName`, `BillingPeriodStartDate`, `BillingPeriodEndDate`, `BillingProfileId`, `BillingProfileName`. São **dois** ajustes separados: um para first-party e outro para marketplace, e não existem em mês aberto.
- Atributos ausentes (ex.: subscription IDs) passam a ser **null ou vazio**, em vez do GUID vazio `00000000-0000-0000-0000-000000000000`. Afeta unused reservations, unused savings plan e ajustes de arredondamento.

## 4. Campos (nomes verificados por contrato)

**Todos os nomes abaixo estão VERIFIED.** O casing é reproduzido **exatamente** como aparece na
página oficial de cada contrato, inclusive onde é inconsistente (ver §6).

**Semântica de `Obrigatório` (campo `required` do `.schema.json`):** significa **"a coluna está
sempre presente no export"** — o provedor enumera a lista de colunas por contrato e versão, e cada
coluna listada é uma posição fixa do arquivo. **Não** significa "o valor nunca é nulo": a nulidade
dos valores é um eixo separado, e para este dataset a Microsoft só a descreve em prosa (ver §5).
Por isso **as 272 colunas são `required: true`, cada uma dentro do seu contrato**.

**Escopo obrigatório — leia antes de usar `required`.** Este dataset é o único do diretório com
**cinco conjuntos disjuntos**. O provedor não publica uma lista única: publica uma lista por
contrato e versão, e essa lista varia. Consequências verificadas:

| Fato | Valor |
|---|---|
| Contratos (conjuntos) | 5 |
| União de todos os nomes distintos | **132** |
| Soma das linhas de conjunto | **272** |
| Nomes presentes nos **5** contratos simultaneamente | **0** |

Ou seja: **nenhum nome de coluna vale para todos os contratos.** `required: true` nesta superfície
é sempre **relativo ao conjunto** (`sets[].name`, ex.: `"Enterprise Agreement (EA) [2024-08-01]"`),
nunca uma afirmação global. Um artefato de um contrato contém **apenas** as colunas daquele
contrato — p.ex. EA `2024-08-01` tem 57 colunas e não contém `meterId`, que só existe em
MCA/MPA/CSP.

> **Limitação conhecida do validador (reportada):** `checker.check()` compara por **nome apenas** —
> `required_names` é achatado sobre todos os conjuntos e `without_contract` considera um nome
> autorizado se for geraVEL em **qualquer** conjunto. Enquanto o escopo não for filtrado por
> conjunto, validar um artefato de EA contra esta spec acusa as colunas dos outros quatro contratos
> como `missing` (falso positivo). O campo `scope` de cada coluna já existe e está correto (272
> chaves distintas); falta o `checker` consumi-lo.

A Microsoft **não publica indicador de obrigatoriedade nem de nulidade por coluna** para o dataset
clássico — nenhuma das páginas de schema por contrato traz coluna de tipo, de nullability ou de
obrigatoriedade. O `required` aqui é, portanto, uma afirmação sobre a **presença da coluna** (lista
fechada e enumerada pelo provedor), não sobre o conteúdo do valor.

> **Tipo / Unidade / Formato data/hora / Valores permitidos = não publicados.** A Microsoft não
> publica esses atributos para o dataset clássico. Estão preenchidos com `—` e **não** foram
> inferidos. No `.schema.json` o campo `type` é **ausente/nulo** (a ausência é a informação
> correta) e a nuance está em `evidence: "name-only"`. Ver §5.

## 5. Campos não comprovados

**Esta é a seção crítica desta superfície.** A Microsoft publica os **nomes** e a **ordem** das
colunas do dataset clássico, mas **não publica** os demais atributos. Tudo abaixo está
`UNVERIFIED` e **não deve ser gerado por inferência**.

| Item | Status | Motivo |
|---|---|---|
| Tipo de dado de **todas** as colunas do dataset clássico | **UNVERIFIED** | Nenhuma página oficial do dataset clássico traz uma coluna "DataType". Compare: a página equivalente do dataset FOCUS publica `DataType` por coluna; a do clássico não. Não existe fonte para afirmar `String`, `Decimal` ou `DateTime` para qualquer coluna clássica. |
| Obrigatoriedade / nullability de cada coluna | **UNVERIFIED** | Não publicada. A documentação descreve casos em que valores *podem* ser null/empty (`ResourceGroup`, `ResourceName`, `ResourceType`, `ServiceName` etc.), mas não define nullability como propriedade formal do campo. |
| Unidade por coluna | **UNVERIFIED** | Não publicada. As descrições em prosa indicam moeda para colunas de custo, mas não há declaração de unidade por campo. |
| Formato de data/hora de `Date`, `UsageDateTime`, `BillingPeriodStartDate`, `BillingPeriodEndDate`, `ServicePeriodStartDate`, `ServicePeriodEndDate`, `ExchangeRateDate`, `UsageDateTime` | **UNVERIFIED** | A única indicação de formato é para `UsageDateTime`: "The usage date of the charge in yyyy-mm-dd format". Para as demais, apenas descrição semântica. **Não há declaração de ISO 8601 nem de UTC para o dataset clássico** (ao contrário do FOCUS, que tem o atributo `DateTimeFormat`). |
| Enumerations completas de `ChargeType`, `Frequency`, `PricingModel`, `PublisherType`, `Term`, `IsAzureCreditEligible` | **UNVERIFIED** | Apenas exemplos ilustrativos em prosa (ex.: "Values: `On Demand`, `Reservation`, `Spot`, and `SavingsPlan`"), **sem tabela de enumeração** e sem garantia de exaustividade. A descrição de `PricingModel` diz "On Demand" com espaço, enquanto outros lugares usam "OnDemand". |
| Casing exato de `PayGPrice`, `payGPrice`, `PricingModel`, `pricingModel`, `Location`, `location`, `InstanceName`, `ResourceId`, `SubscriptionId`, `subscriptionId` | **UNVERIFIED** | O casing **varia entre contratos e entre versões do mesmo contrato**. Ver §6, divergências 2–4. Um simulador multi-contrato precisa escolher por contrato **e** por versão e registrar; não há regra única. `benefitId`/`benefitName` **não** entram aqui: as duas fontes oficiais usam minúsculas. |
| Separação *actual* vs *amortized* no nível de colunas | **UNVERIFIED** | A Microsoft documenta actual e amortized como **datasets distintos** no portal e na API (`ActualCost` / `AmortizedCost`), mas o índice de schemas publica **um único** schema "Cost and usage details" por contrato. Nenhum documento afirma que actual e amortized têm exatamente a mesma lista de colunas. |
| Nomes de arquivo / partição do dataset clássico | **UNVERIFIED** | A convenção documentada é "avoid hardcoding or guessing partition names"; o manifesto é a fonte. Ver `cost-management-export-manifest.md`. |
| Prefixo de coluna para `ActualCost` vs `AmortizedCost` | **UNVERIFIED** | Não documentado. |
| Codificação oficial do CSV | Parcialmente comprovado | O tutorial manda usar `File origin 65001: Unicode (UTF-8)` no Excel, o que **sugere** UTF-8, mas não há declaração explícita de encoding para o dataset clássico (o FOCUS tem `StringEncoding: UTF-8` nos metadados). Tratar como **UNVERIFIED** até confirmação. |
